# 从 Work 文档自动准备进化评测

Work 开启自动进化后，不再要求用户先填写目标、优化文件、训练命令和留出命令。没有配置的 Work 持续空闲后，使用现有 AuxiliaryAgent 读取 `SESSION.md`、相关 Markdown、实际目标文件和已有检查，准备一个可离线运行的小范围实验。已手动保存的配置继续复用。

入口位于「工作 → 后台任务 → 自动进化」。这里显示读取文档、验证评测、自动迭代、等待采纳四个阶段；展开准备记录可查看来源、目标和验收原文、基线分数、正反对照结果及 Token 用量。缺少真实验收依据或离线依赖时显示具体缺项，用户可以补充信息后重新准备，也可继续使用手动配置。不会因超时、关闭客户端或未答复而自动选择答案。

## 执行链路

`Automatic` → `preparation.prepare` → `AuxiliaryAgent.prepareWorkEvolution` → `submit_work_evaluation` → 沙箱试跑 → 保存冻结配置 → `AntOmniEvo` → 新上下文的 `AuxiliaryAgent.iterateWork` → 等待人工采纳。

- 准备工具只有 `list_work_files`、`read_work_file`、`submit_work_evaluation`、`report_work_blocker`。原始 Work 只读；不提供 shell、网络、Git 写入或设备工具。
- 无 Token 上限的准备默认每次读最多 32,000 字符，较大的文件可按偏移继续读；保留数值预算的调用仍用小分页。文件定位支持名称模式与有限递归（8 层、5,000 个目录项、最多返回 60 项），跳过链接与私有目录。优先定位文档引用的文件，避免逐层浏览大仓库反复消耗输入 Token。
- 提供宿主实际探测到的 `/usr/bin` 运行时状态，避免假定 home 下的构建工具可以在沙箱内使用。自动准备不再按 Token 额度或 6 步探索门槛提前关闭读取工具。
- 模型提出明确的目标、输入文件、两个检查、生成文件、Markdown 原文引用和正确/错误实现对照。宿主验证引用存在且仍与已读版本一致。
- 已标记完成的行为也可作为回归与边界评测对象，不要求遍历全部未完成事项。连续读取最多 8 轮后进入提交阶段，必须试跑草稿或记录具体缺项；获得试跑反馈后恢复读取，累计 Token 用量不设上限。SDK 工具错误与宿主阶段校验均纳入记录，不能用旧读取工具绕过提交阶段。基线已通过时允许得出“保留原方案”。对照支持完整内容或唯一匹配的 `find/replace`，所有修改均以原始目标为基准在副本中应用。
- 可先以 `controls=[]` 试跑完整草稿，返回评分与有界检查输出，便于修复编译及运行错误。宿主缓存成功草稿，下一次可以仅提交 `controls`，无需重复生成检查文件；修改目标或检查则须提交完整计划。草稿不会发布配置或启动实验，追加对照后仍完整重跑基线及正反对照。
- 草稿通过后，模型进入独立的对照上下文：只携带用户约束、完整已验证计划、原始优化文件和试跑证据，随后正常累积工具反馈，不再带入此前探索与推理历史。草稿另存为同版本目录内的 `draft.json`，用于诊断；仅有草稿仍不能启动实验，也不会在服务重启后自动跳过验证。
- 输入以确切文件列表复制，上限 5,000 个文件、100 MiB；只选 1–10 个实际优化文件。不遍历无关仓库、链接或大型构建产物。被选中的链接、共享硬链接、越界路径仍拒绝。
- 生成的评测只在 `__lucyna_eval__/` 私有目录中出现，最多 30 个文件、合计 512 KiB，全部冻结。训练与留出使用不同命令和互不重叠的冻结文件；仅重命名相同检查会被拒绝。同一通用检查器可通过不同命令参数提供不同输入，不会仅因程序内容相同而被误拒绝。
- 每个检查在现有 bwrap 沙箱中执行：Work 与 `/usr` 只读、`/tmp` 可写、无网络与用户主目录。评分最后一行必须输出 `score` 或 `passed/total` JSON，且退出码有效。
- 基线连续运行两次必须稳定；正确对照必须在两个检查中都满分，错误对照必须在两个检查中都被拒绝。任何一步失败均不发布配置；模型可以根据试跑错误继续修正。
- 两组检查须覆盖相同验收行为并使用不同输入，不能把不同功能分别当作训练和留出。若训练基线失败而留出满分，宿主拒绝发布并要求修正覆盖：当前优化器按留出改善选优，此组合无法验证已观察问题的修复。两组基线均满分的回归评测仍可发布，最终允许无改进。
- 配置保存在服务目录 `preparations/<Work 根哈希>/<版本>/compiled.json`。客户端只持有不透明版本 ID，不能指定任意评测路径，也不能修改已冻结的检查。
- 迭代使用新的 agent 上下文，不带入生成评测时的对话、正确实现对照或留出内容。生成的检查不会写回原 Work。采纳/回退沿用文件哈希校验，公共 L3 和 skill 不参与修改。

## 调度与恢复

自动准备与自动生成的实验配置均使用 `tokenBudget: null`，不设置累计 Token 上限，也不额外设置单次模型输出上限，输出长度遵循模型服务限制。用量仍持久化展示；中断时保留已知用量并标记可能不完整，不伪造“预留额度”。手动配置中明确填写的数值预算继续生效，普通 OMP 后台任务仍沿用原有预算规则。

仅当 Work 准备/迭代使用 Chat Completions 的 `MiniMax-M3.1-Flash`（含提供方前缀）时，显式设置 `reasoning_effort=high`。[MiniMax 官方文档](https://platform.minimax.io/docs/api-reference/text-openai-api)说明该模型省略此项默认 `max`；此处调节推理深度，不限制 Token 数量，也不修改其他模型、标题等功能或用户保存的配置。

准备保留 30 分钟总超时、10 分钟单步超时和 64 步循环保护；无 Token 上限的迭代使用同样的 agent 时限，且仍受实验时间、候选轮数和取消机制约束。长模型请求使用独立的 Undici 连接池，让响应头/响应体等待时限与单步时限一致，避免默认 300 秒传输等待先于 agent 截止请求。每个 Work 滚动 24 小时最多准备 2 次；自动实验仍沿用空闲 60 秒、至少间隔 30 分钟、滚动 24 小时最多 2 次的规则。准备与自动实验全局串行。

失败和缺项不会按心跳无限重试。显式重新准备或相关 Markdown 变化才会再次尝试，仍受每日限额约束。自动配置会检查 `SESSION.md`、`notes/*.md` 和其他实际读过的 Markdown；修改或删除引用文档会使旧配置失效。手动配置不会因此被替换。原文件并发变化会阻止发布过时评测；实验与采纳阶段也会重新核对所选输入。

暂停会取消准备请求；服务重启保留中断记录与预算，不自动补写配置。普通会话可以继续使用 Work，自动迭代在私有副本中执行。辅助模型密钥仅经私有管道交给 agent，不进入配置、实验目录、日志或 OMP journal；准备和迭代均不新增 OMP session。

## 验证

```powershell
node --test test/auxiliary-agent.test.cjs test/evolution-agent.test.cjs test/work-runner.test.cjs
node node_modules/typescript/bin/tsc --noEmit
node_modules/electron/dist/electron.exe test/work-preparation-desktop.cjs
```

在 WSL 的仓库根执行 Python 验收：

```bash
python3 -m unittest discover -s test -p 'work_*test.py'
```

Python 集成测试使用本地模型协议夹具，经真实 AI SDK、bwrap 和已安装的 AntOmniEvo 跑到 `waiting_review`，再验证人工采纳与回退、原 Work 不被提前修改和凭据不落盘。没有安装 AntOmniEvo 时，该条集成测试会明确跳过；其他规则测试继续执行。

桌面验收加载正式渲染器和合成准备状态，检查读取进度、缺项补充、重试、暂停、冻结配置、四种主题及窄窗。结果和截图位于忽略目录 `.runtime/work-preparation-ui/`。它验证界面与交互，不代表真实模型生成质量。真实模型验收使用隔离 Work 与私有配置管道，不能把协议夹具通过当成真实模型通过。

2026-11-02 使用已配置的 MiniMax-M3.1-Flash 完成一次真实模型隔离验收：从算术回归 Work 的 Markdown 准备评测，正反对照通过后由 AntOmniEvo 迭代，留出评分从 0 提升到 1，最终停在 `waiting_review`。用时约 87 秒，准备消耗 26,334 Token，迭代消耗 16,807 Token；原文件未变，没有 OMP session。这验证真实调用链，不代表复杂设备 Work 的目标都能自动转成离线评测。

早期版本另一次真实模型隔离验收用时约 126 秒，基线 2/11 提升到 11/11，停在 `waiting_review`；准备 34,968 Token、迭代 20,033 Token，原文件与 OMP 会话数仍未改变。当前自动化回归为 66 项 Python、36 项 Node 全通过；TypeScript 与渲染器构建通过，桌面合成状态通过四套主题的深浅色和窄窗验收。

同日对已有大型 C++/设备 Work `rx101-perf-monitoring` 使用隔离服务目录验收，未重启生产客户端或服务。最初暴露了探索预算耗尽、模型输出截断、默认 300 秒传输等待、对照错误诊断不足与重复提交大计划等问题；已经取消自动流程的 Token 限制，调整长请求传输及分阶段提交，并补充回归覆盖。

无需人工填写目标或检查命令的一轮已完成：agent 从原 Work 文档自行选择 Timeline 有界环、窗口和触发合并行为，生成两套 C++ 探针与 Python 检查；训练 29/29、留出 51/51。两组正确对照均满分，两组错误对照均被两套检查拒绝。准备约 1,200 秒，随后真实 AntOmniEvo 约 100 秒完成，状态 `completed / no_improvement`，基线与最佳留出分数均为 1。原始输入未修改，未创建 OMP session。此轮直接使用 g++ 的局部探针，不应视为已执行原项目全部 Bazel 测试或板端验收。证据位于 `.runtime/work-preparation-live/rx101-result.json`、`compiled-rx101.json` 和 `rx101-evolution-result.json`。

正式渲染器也加载了该次隔离实测的只读快照，结果与截图位于 `.runtime/work-preparation-real-ui/`；没有将测试记录写入生产服务。由真实长文本发现并修复了结果被挤到面板下方的问题：长目标和验收标准可展开完整查看，结果分数保持可见，未发现改进时不再提示有候选等待采纳。

另做了带独立缺陷线索的 rx101 验收：目标是 `SnapshotReporter` 对长控制字符 reason 的 JSON 输出。独立于模型检查的 C++ 探针覆盖 42 组输入、168 条输出，原代码稳定出现 8 条截断的非法 JSON；探针同时核对进程退出码、每组输出条数、事件种类和 reason 往返，不能用省略输出通过检查。此轮属于有明确线索的测试，不能计作自动发现缺陷。

该复杂缺陷链路尚未通过验收。一次尝试触到模型服务原生的 131,072 输出 Token 上限；另一次草稿训练 50%、留出 100%，暴露两组覆盖行为不一致，未作为可用改善证据。最后一轮约 1,767 秒后准备失败，已记录 364,978 Token，末次请求用量可能不完整；最后两次提交被检查内容重复规则拒绝，未发布配置，也未启动候选迭代。原文档未变，隔离进程已退出。证据位于 `.runtime/work-preparation-guided/result.json`、`run.log` 和 `independent-original.json`。

最后一轮运行期间与结束后补充了明确的字段错误/超时诊断，以及“相同通用检查器、不同参数输入”的合法边界检查；这些修正已通过回归，但没有把上述失败记录改写为成功，也尚未在该复杂缺陷上完成新一轮真实模型闭环。当前可确认实际 Work 的自动准备与无改进完成链路、简单回归 Work 的候选生成/人工采纳链路；不能据此宣称所有复杂设备 Work 都能稳定零配置进化。生产客户端及服务未为验收重启。

生成的检查只能证明选定范围内的离线行为。设备性能、线上效果、业务阈值和长期泛化仍需对应的真实依据与独立验收；正反对照可以排除明显无效评分器，不能证明自动生成的用例覆盖了全部业务语义。采纳始终由用户确认。
