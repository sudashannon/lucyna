# Design System: Lucyna

## Overview

**Creative North Star: "Four Ways Into the Same Work"**

Lucyna offers four visual schemes for the same local Work loop. Blue keeps application navigation and the Work directory in separate columns, with a cool reading plane and cobalt selection. Classic retains the original compact neutral interface. Folio joins navigation and Work in a forest-green sidebar beside warm paper surfaces, with serif styling confined to reading headings. Pixel uses a charcoal sidebar, periwinkle selection, square controls, and the original geometric wordmark.

Light and Dark are independent appearances within Blue, Classic, Folio, and Pixel. Theme changes affect presentation while the current Work, session, transcript, and mounted draft stay in place. The silver-haired character and black cat remain the existing illustration assets; Pixel adds only the original 5×7 geometric SVG wordmark.

**Key Characteristics:**
- Blue keeps its separate application navigation and Work directory.
- Classic keeps the original compact neutral palette and horizontal navigation.
- Folio pairs a forest sidebar and sage accents with warm paper and spacious reading.
- Pixel pairs a charcoal sidebar with periwinkle selection, compact sans text, and four-pixel controls.
- Every scheme has independent Light and Dark palettes.
- Existing character and cat artwork remain shared brand assets.

## Colors

Four palette families share the same Work loop. The frontmatter records the renderer’s literal Blue and Classic values and every color-valued Folio and Pixel root palette property in both appearances. Folio and Pixel also expose the sidebar’s semantic text remaps as distinct tokens, while the sidebar surface, selection, border, and focus aliases are described below.

### Primary

- **Studio Cobalt:** Blue actions and selected destinations use the existing cobalt roles.
- **Folio Forest Action:** Folio’s light action uses the forest accent; its dark action switches to the lighter sage accent.
- **Pixel Periwinkle Action:** Pixel uses a periwinkle action and a lighter periwinkle accent in Dark.
- **Classic Graphite Action:** Classic keeps its original monochrome action.

### Secondary

- **Blue Navigation Navy:** Blue keeps a dedicated navy application rail, separate from its pale Work directory.
- **Folio Forest Sidebar:** Folio uses forest green for the shared navigation and Work sidebar, with sage selection.
- **Pixel Charcoal Sidebar:** Pixel uses charcoal for the shared sidebar and periwinkle for selection.
- **User Message Surfaces:** Each theme separates user-message fill from the main reading surface.

### Neutral

- **Folio Paper and Ink:** Warm paper, elevated ivory, and forest-tinted ink form the light reading palette; Dark uses deep green surfaces and warm light text.
- **Pixel White and Graphite:** Cool white and graphite form the light reading palette; Dark uses charcoal-blue surfaces and pale lavender text.
- **Classic Paper and Graphite:** The existing neutral light and dark surfaces remain available.
- **Blue Reading White and Primary Ink:** The original bright Blue reading plane and separate dark palette remain intact.

**The Four-Scheme Rule.** Keep Blue, Classic, Folio, and Pixel as distinct visual schemes. Each scheme has independent Light and Dark appearances; appearance mode is not another scheme.

**The Sidebar Role Mapping Rule.** In Folio and Pixel, primary and body-strong sidebar text map to navigation ink; muted-readable, secondary, and placeholder text map to navigation muted. The sidebar surface uses studio-nav; elevated surfaces, chips, and hover use studio-nav-hover; selection uses studio-selection; borders and input outlines use studio-nav-border; focus uses studio-nav-ink.

## Typography

**Display Font:** Source Han Sans SC, bundled as a variable font, with Microsoft YaHei, system-ui, and sans-serif fallbacks.
**Body Font:** Source Han Sans SC, with the same fallback stack.
**Label/Mono Font:** The interface uses the body stack for labels and Cascadia Mono, Consolas, Source Han Sans SC, ui-monospace, monospace for code.

**Character:** Blue and Classic keep the compact Chinese interface hierarchy. Folio uses the CSS-declared serif stack for the brand and sustained-reading headings, while message copy stays in the bundled sans font. Pixel keeps all interface text in the bundled sans font and confines its bitmap geometry to the wordmark SVG. The renderer bundles Source Han Sans only; availability of the Folio serif fallback families depends on the operating system.

### Hierarchy

- **Display:** Blue welcome heading (28px); Folio welcome and knowledge headings (28px, 600, 1.5).
- **Brand:** Blue wordmark (22px); Folio brand word (25px, 600, 1.3).
- **Current Work:** Blue work heading (21px); Folio heading (23px, 600, 1.5); Pixel heading (18px, 600).
- **Reading headings:** Folio assistant and knowledge headings (24px, 600, 1.6); Pixel assistant heading (20px, 650, 1.5).
- **Work details:** Folio identity heading (23px, 600); Pixel identity heading (19px, 650); Pixel knowledge page title (23px, 650).
- **Body:** Classic, Blue and Pixel messages use 15px; Folio uses 16px with its existing 1.95 leading. Narrow Folio/Pixel messages retain a 15px reading floor. Composer and document prose use 15px.
- **Navigation:** Blue destination tabs (15px); Folio and Pixel destination tabs (14px); compact Knowledge subnavigation (13px).
- **Labels:** Common UI and Cindy buttons use 14px, compact copy uses 13px, supporting captions use 12px, and code/terminal text uses 13px. Semantic `--font-size-*` tokens in `src/renderer/tokens.css` own the scale. Existing heading sizes, illustration sizes, chart tick labels and layout columns are preserved.

**The Folio Reading Stack Rule.** Keep the declared Source Han Serif SC, Noto Serif CJK SC, Songti SC, SimSun, serif fallback stack to the Folio brand and reading headings. Body text remains Source Han Sans; the repository does not bundle a serif face.

**The Pixel Wordmark Rule.** Keep the original 5×7 geometric SVG lettering in the Pixel wordmark only. Chinese interface copy remains normal Source Han Sans text.

## Layout

Blue’s expanded Workbench and Knowledge use the same top bar, primary navigation, and compact page heading. The single left directory changes with the section and keeps its own width, filters, and reading position. In Workbench it groups local and SSH Work and keeps the task companion at the bottom. Work row menus can pin a Work above the host groups, with the most recent pin first. Blue’s row menu can also park a Work in a collapsible section. Pinning a parked Work brings it back into the main list, and parking a pinned Work removes the pin. Collapsed or narrow Blue navigation uses the compact rail. Classic retains the single-sidebar shell and horizontal navigation. Folio and Pixel use a resizable Work sidebar, defaulting to 248px within a 200–420px range, with vertical primary navigation above the Work list. New Work is the directory-level primary action. New Chat sits beside the selected Work as a separate button, with an icon-only form below a 280px row width. Collapsed and narrow navigation retains both shortcuts.

Group the Work directory by execution host, with recent-use sorting available across hosts. Work selection and session disclosure have separate controls. By default, expand the selected Work and surface the most urgent session status on a collapsed Work row. The companion illustration opens the existing cross-Work active sessions view. In a collapsed rail or short window it uses a compact image and keeps its activity count and accessible name.

The Knowledge sidebar has its own independent 340px default width and 280–480px range. All four themes use one compact column of navigation entries. The active group's child pages sit directly below their parent; only the current leaf uses the filled selection state, while the parent uses stronger text and an expanded chevron. The source selector has a visible scope label below navigation, and source capture requires choosing one source. Navigation scrolls within short windows; the document library retains its separate scrolling area and reading position. Adding a source is a compact outlined action, with refresh alongside. The companion occupies a 120px-high slot at the foot of the wide Folio/Pixel sidebar only when the window is taller than 820px; it is hidden while Knowledge is open, in the compact rail, and in short windows. The redundant informational profile row stays hidden, while the runtime and action footer remains available.

At 760px and below, Folio and Pixel use the existing 64px compact rail. At 1280px and below, the tools panel becomes the existing overlay drawer. The conversation stays the central reading surface; Folio uses a wider, more open transcript and composer, while Pixel uses tighter insets and a shorter composer. Blue keeps its separate reading and inspector columns when space permits.

The visual scheme persists under lucyna.visual-theme; an unknown stored value falls back to Blue. The Light/Dark appearance persists separately. The header selector applies immediately; settings keep the theme in a draft until Save, and Cancel keeps the active scheme. Switching visual schemes preserves the mounted conversation, composer draft, active session, and transcript.

## Elevation & Depth

Exact retained and added shadow values, easing, and durations live in the sidecar.

### Knowledge review queue

The **待核实** view uses a compact document queue, capped at 340px on wide layouts, beside a left-aligned detail pane. Each row shows the document title once, followed by the issue in plain Chinese and its named source. Search, issue-type filtering, and the option to include ignored findings stay together above the queue. The selected detail presents the title, source and review position, a concise reason and next step, grouped actions, and a preview of the current original. Raw rule codes and checker output belong in a collapsed detail disclosure.

Structural findings lead with **查看原文**; evidence findings retain explicit confirmation and retraction. **忽略此版本** is a quieter text action, with its version scope stated beside the decision area. Preserve version checks and error recovery. Below the existing 900px content-container breakpoint, show the queue and detail sequentially, hide filters while reading, and retain **返回列表**. Colors, typography and focus states follow all four schemes and their light/dark appearances.

**Agent 处理建议** sits before the source preview as one reading section, separated by a fine divider. Opening a record reads existing valid advice; **生成处理建议** explicitly starts a model request. Present a document-specific summary, short action steps, optional proposed text, unanswered questions, and links with exact source excerpts. Keep pending and retry states local to this section. Selecting another finding or receiving changed context must not expose an older request as current advice. Suggestions remain distinct from confirming a finding or editing the document.

**删除文档** is a quiet destructive action after the review actions. A focused confirmation identifies the document, named source and exact path, explains that all of its findings leave the queue, and states that local history is retained. Keep the target and operation identity stable during retries. Version conflicts remain visible in the dialog; successful deletion removes the document’s findings together and refreshes the directory. Distinguish completed deletion with a pending index refresh from a failed delete.

### Work files and Git review

In expanded Blue, **对话工作**, **工作区文件**, and **活跃会话** stay anchored beside the left directory as the inspector opens or closes across pages. Appearance and browser shortcuts live in the shared top bar. The terminal and **工作区改动** stay available for the selected Work across all three pages. The latter opens the conversation alongside current Git state and identifies the member, branch, file, and staging scope. A prompt with a saved record has a **查看改动** action. The expanded Blue workbench places this action beside the latest completed run, while earlier turns keep their own actions. **本轮改动** compares the working tree before sending and after the session settles. The panel shows its capture interval, indicates partial records, and links back to current Git state. Both views dock beside the conversation on wide windows and use the keyboard-accessible drawer on narrow windows. A selection or bounded patch can be added to the active draft.

The tools panel defaults to **工作详情**. Its **进展** view shows the registered Work goal and status from `SESSION.md`. Assistant replies and per-turn review actions stay in the conversation.

The Work assistant summary is a compact reader: an expandable overview followed by count-bearing tabs for next steps, open questions, decisions, goals, and progress. Keep one section visible at a time, with four entries initially and an explicit control for the remainder. Preserve the existing item order and text; long entries expand from a three-line preview. Separate entries with fine rules and whitespace, without decorative cards or implied priorities. Each item has one compact original-message link; additional citations expand inline as links, never as duplicated source prose. Full session names remain available in accessible names and hover titles. Tab selection supports arrow keys, Home, and End; narrow panels wrap controls instead of clipping them. Draft continuation still includes the summary across all sections.

The Work content keeps **对话工作** and **工作区文件** mounted as sibling surfaces, so changing tabs preserves the conversation draft, terminal, opened files, and reader positions for that Work and host while the client stays open. File browsing and Git review use the main Work width. The file surface groups **浏览、改动、历史、分支、Worktree** under one secondary navigation; the reader reuses the existing document reader, while diff additions and deletions use semantic status colors and explicit labels.

Keep the repository selector and current branch context visible beside the view controls. Changes distinguish staged, unstaged, and registered-baseline comparisons, with whole-file or server-validated hunk/line staging and unstaging. Commit only the reviewed index contents; retain normal hooks and signing, guard the reviewed tree and parent, and preserve independently staged changes. Fetch and push name the configured remote and target, verify the resulting remote ref, and never force-push. History provides message filtering and paged results; branch selection compares the chosen ref with `HEAD`, while branch management creates or switches a branch and permits fast-forward-only merges. Worktree management is limited to registered members of the selected Work.

Keep write state legible: durable operation IDs and recent history accompany progress, reconciliation, and an explicit user acknowledgement after an uncertain result. Do not imply that an interrupted write is automatically retried. Branch/worktree lifecycle actions require a clean tree and no active Work session; the Worktree manager refuses dirty, untracked, or locked members. During WSL lifecycle operations, a socket-owned lease blocks WorkRunner ordinary and automatic task admission; closing the owning socket releases it. There is no conflict editor, and diverged merges remain a terminal task. Git credentials, hooks, and signing configuration stay on the execution host; interactions that need user input are handled in that host's terminal. SSH uses the same surfaces only when the host advertises the workspace capabilities.

At wide sizes, pair a 280px list with a flexible reading area; Worktree details use the full area. At a file-surface container width of 720px or less, expose the list and reader progressively. Enable split diffs only when the file-surface container reaches 1120px. Controls inherit the active scheme's surface, border, accent, and status tokens; the existing eight-pixel control radius narrows to six pixels in Folio and four pixels in Pixel. Commit messages and pending operation IDs persist per Work/host/member in local storage; opened files and reader positions stay in client memory and do not survive a restart.

## Do's and Don'ts

### Do:

- **Do** keep all four visual schemes and their independent Light/Dark appearances.
- **Do** retain Blue’s separate application navigation and Work directory; Folio and Pixel share the resizable 248px Work sidebar.
- **Do** keep Source Han Sans for interface and body text. Folio’s serif fallback stack is scoped to the brand and reading headings.
- **Do** keep Pixel’s original 5×7 geometric SVG lettering in the wordmark only; Chinese interface copy stays typographic.
- **Do** preserve the existing silver-haired character and black cat assets and their theme-specific placement.
- **Do** preserve Work, session, draft, and transcript state while switching schemes.
- **Do** use the runtime and action footer in the compact Folio/Pixel sidebar.

### Don't:

- **Don't** describe Blue, Classic, Folio, and Pixel as Light/Dark appearance modes.
- **Don't** merge Blue’s separate navigation and Work directory into the Folio/Pixel sidebar layout.
- **Don't** make Folio body copy serif or Pixel Chinese copy bitmap-style.
- **Don't** add new illustration assets or replace the existing character and cat.
- **Don't** add a redundant informational profile row to the Folio/Pixel sidebar.
- **Don't** invent runtime statuses, Work counts, knowledge records, or session facts.
